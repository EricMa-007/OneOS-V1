## 一、项目概览

### 1.1 项目基本信息

| 项目 | 说明 |
|------|------|
| **项目名称** | OneOS Core（灵魂级个人操作系统） |
| **当前版本** | V1.0 · 20260824 快照 |
| **代码总量** | 48个JSX组件 + 5个CSS样式文件 + 2个HTML入口 |
| **总代码行数** | 约 15,000 行（含注释和空行） |
| **技术栈** | React 18 + Babel Standalone + 原生CSS + Python HTTP Server |
| **架构模式** | 数据与视图分离 + 全局状态发布订阅 + 组件化 |
| **支持平台** | 桌面端（Web）+ 移动端（响应式H5） |

### 1.2 设计原则

1. **零构建依赖**：不使用 Webpack/Vite 等构建工具，直接用 Babel Standalone 在浏览器端编译 JSX，降低入门门槛
2. **本地优先**：所有数据存储在本地，Markdown 为唯一数据结构，不依赖云端
3. **数据与视图分离**：每个功能模块都有独立的 `*-data.jsx`（数据层）和 `*-view.jsx`（视图层）
4. **全局设计系统**：统一的设计令牌（Design Tokens），确保视觉一致性
5. **双端共用一套逻辑**：桌面端和移动端共用同一套组件逻辑，仅通过 `isMobile` 状态和 CSS 媒体查询做 UI 适配

## 三、核心技术架构

### 3.1 技术栈选型

| 层级 | 技术选型 | 选择理由 |
|------|----------|----------|
| **UI框架** | React 18（生产版） | 组件化、生态成熟、Hooks 机制适合复杂状态管理 |
| **编译** | Babel Standalone（浏览器端） | 零构建依赖，直接在浏览器中编译 JSX，降低入门门槛 |
| **样式** | 原生CSS + CSS变量 + 内联样式 | 无需CSS-in-JS库，性能好，调试方便 |
| **状态管理** | 自研发布订阅模式 + React Hooks | 轻量、无依赖、板块间数据联动 |
| **数据格式** | Markdown + Frontmatter | 人类可读、版本控制友好、本地优先 |
| **服务器** | Python http.server | 零依赖、跨平台、适合开发阶段 |
| **移动端** | 响应式H5 + isMobile状态 | 一套代码双端适配，无需原生开发 |

### 3.2 为什么不使用构建工具

OneOS V1 选择**零构建依赖**的架构，原因如下：

1. **降低入门门槛**：任何人克隆项目后，直接用 Python 起一个 HTTP 服务器就能运行，不需要安装 Node.js、npm、Webpack
2. **快速迭代**：修改 JSX 文件后刷新浏览器即可看到效果，不需要等待构建
3. **透明可控**：所有代码都是人类可读的，没有被打包压缩，便于学习和调试
4. **本地优先**：不依赖 npm 注册表，所有依赖都在 `vendor/` 目录中，离线可用

**未来规划**：当项目成熟、需要生产部署时，可以引入 Vite 或 esbuild 进行构建优化，但 V1 阶段保持零构建。

OneOS 采用**自研的发布订阅模式**进行全局状态管理，核心代码在 `app-state.jsx` 中。

#### 核心设计

```javascript
// 状态结构
state = {
  dashboard: { ... },     // 仪表盘统计
  calendar: { ... },      // 日历强度（按日期存储）
  notes: [ ... ],         // 笔记列表
  graph: { nodes, edges },// 图谱节点
  social: { messages },   // 社交消息

archiveCircleTopic()         // 圈子话题归档 → 更新仪表盘+日历+圈子知识库
```

#### 创新点：板块间数据自动联动

传统应用中，每个板块的数据是孤立的。OneOS 的全局状态管理实现了**板块间数据自动联动**：

- 你在编辑器中写了一篇笔记 → 仪表盘的"今日笔记数"+1 → 日历的当日强度+1 → 知识图谱新增一个节点
- 你和AI进行了一场对话并归档 → 仪表盘的"知识数"+1 → 日历的当日强度+1 → 知识图谱新增"问题-回答"两个节点和一条边
- 你在社交中进行了一次深度对话 → 仪表盘的"深度对话数"+1 → 日历的当日深度因子+1 → 自动生成对话记录笔记
- 你把一篇笔记升维为卡片 → 仪表盘的升维层级统计更新 → 日历的当日升维因子+1 → 知识图谱节点类型变化

**这意味着：你的每一个动作，都会在整个系统中产生涟漪效应。OneOS 不是10个独立的工具，而是一个有机的整体。**

### 3.5 双端适配架构

OneOS 采用**一套代码双端适配**的策略，桌面端和移动端共用同一套组件逻辑。

#### 适配策略

```
┌─────────────────────────────────────────────────────┐
│                  一套组件逻辑                          │
│  app.jsx + 10大板块组件 + 通用组件                    │
├─────────────────────────────────────────────────────┤
│                                                         │
│  ┌─────────────────────┐  ┌─────────────────────┐   │
│  │   桌面端适配层       │  │   移动端适配层       │   │
│  │                     │  │                     │   │
│  │  index.html         │  │  mobile.html        │   │
│  │  (飞书CDN/本地vendor)│  │  (本地vendor)       │   │
│  │                     │  │                     │   │
│  │  isMobile = false   │  │  isMobile = true    │   │
│  │  三栏布局            │  │  单栏布局            │   │
│  │  侧边栏常驻          │  │  侧边栏抽屉式        │   │
│  │  顶部导航            │  │  底部导航            │   │
│  │  design-system.css   │  │  + mobile.css       │   │
│  │                     │  │  + design-system-v2  │   │
│  └─────────────────────┘  └─────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

#### 三层适配机制

1. **组件级 isMobile 状态**：每个需要响应式的组件都有 `isMobile` 状态，通过 `window.innerWidth <= 768` 判断，根据状态渲染不同的布局和样式
2. **CSS 媒体查询**：`mobile.css` 中所有规则包裹在 `@media(max-width:768px)` 中，覆盖桌面端样式
3. **设计系统V2覆盖**：`design-system-v2.css` 提供移动端专用的设计令牌覆盖（按钮触摸区、图标尺寸、日历等比等）

#### 移动端导航 V4 架构

移动端底部导航经历了4次迭代，最终采用 **data-nav-id 精确匹配**方案：

```
V1：文本匹配 → 失败（标签被覆盖，social='社交' vs '连接'）
V2：位置匹配 → 失败（侧边栏按分组排列，顺序与全局不一致）
V3：自动展开分组+位置匹配 → 部分成功（仍有错位）
V4：data-nav-id 精确匹配 → 成功
    - sidebar.jsx 每个导航按钮添加 data-nav-id={item.id}
    - mobile-nav.jsx 通过 document.querySelector('button[data-nav-id="calendar"]') 精确匹配
    - MutationObserver 保证汉堡菜单常驻
    - 抽屉遮罩纯半透明黑色（非blur），z-index 9998
    - 侧边栏 z-index 9999，底部导航 z-index 9000
```

## 四、核心创新点

### 4.1 创新一：知识升维四层模型

**这是 OneOS 最核心的原创方法论。**

传统知识管理工具只有"收集"和"搜索"两个动作。OneOS 提出了**四层升维模型**，将知识加工过程结构化：

```
原文(Source) → 卡片(Card) → 摘要(Summary) → 元知识(Meta)
  100%          31%           8%             2%
  低价值密度    中价值密度    高价值密度     极高价值密度
```

**技术实现**：
- `elevation-data.jsx` 定义四层数据结构
- `elevation-view.jsx` 实现漏斗可视化、卡片墙、升维操作
- `app-state.jsx` 的 `elevateNote()` 方法实现升维动作的全局联动
- 每次升维自动更新仪表盘统计、日历强度、图谱节点类型

### 4.2 创新二：人类节点（Human Node）

**重新定义"人"在知识系统中的位置。**

传统社交中，"人"是关系的对象；OneOS 中，"人"是知识网络中的节点，和笔记、话题、AI 处于同一层级。

**技术实现**：
- `human-data.jsx` 定义人物档案（id/name/role/topics/x/y/color）
- `human-view.jsx` 实现人网络可视化（力导向布局）
- `human-detail.jsx`（67.9KB，最复杂的单组件）实现人物详情页
- `graph-view.jsx` 中将人节点与话题节点、笔记节点混合展示
- 人与人之间通过"话题交集"建立连接，而非"加好友"

### 4.3 创新三：全局状态联动引擎

**板块间数据自动联动，一个动作产生系统级涟漪。**

传统应用中，每个功能模块的数据是孤立的。OneOS 的 `app-state.jsx` 实现了**5大核心动作的全局联动**：

| 动作 | 触发的联动 |
|------|-----------|
| 新建笔记 | 仪表盘+1 → 日历强度+1 → 笔记列表新增 → 升维raw层+1 |
| AI对话归档 | 仪表盘知识+1 → 日历强度+1 → 图谱新增Q-A节点和边 → raw层+1 |
| 社交消息归档 | 仪表盘深度对话+1 → 日历深度因子+1 → 生成对话记录笔记 → 社交记录新增 |
| 知识升维 | 仪表盘层级统计更新 → 日历升维因子+1 → 图谱节点类型变化 |
| 圈子话题归档 | 仪表盘知识+1 → 日历强度+1 → 圈子知识库新增 → 笔记列表新增 |

**技术实现**：发布订阅模式 + 不可变状态更新 + 浅比较优化重渲染

### 4.4 创新四：零打扰社交规则引擎

**系统性地解决社交焦虑。**

`social-rules.jsx` 实现了一套完整的零打扰社交规则引擎：

- **静默收件箱**：消息到达不通知，用户主动查看
- **时间窗口**：只在设定时间段内接收消息
- **无在线状态**：消除"已读不回"焦虑
- **无已读回执**：回复时间是用户的自由
- **消息过滤**：按话题、人物、重要性过滤
- **深度对话优先**：长消息、有质量的对话优先展示

### 4.5 创新五：极小圈子硬限制架构

**用技术约束保证深度。**

`circle-view.jsx` 和 `circle-data.jsx` 实现了极小圈子的硬限制：

- **人数硬限制**：每个圈子最多10人（代码层面强制校验）
- **圈子数硬限制**：每人最多3个圈子（代码层面强制校验）
- **无消息流**：没有无限滚动的聊天记录，只有共享协作文档
- **自动沉淀**：讨论中的关键观点自动提取为卡片
- **退出自由**：随时退出，知识沉淀归个人所有

**设计哲学**：用技术的"硬限制"对抗社交的"无限扩张"，保证每一个圈子都是深度思考的空间。

### 4.6 创新六：双端零构建适配架构

**一套代码，双端运行，零构建依赖。**

- 桌面端和移动端共用同一套 React 组件
- 通过 `isMobile` 状态 + CSS 媒体查询 + 设计系统覆盖三层适配
- 所有依赖本地化（React/ReactDOM/Babel 都在 vendor/ 目录）
- 不需要 Webpack/Vite，Python http.server 即可运行
- 移动端入口 `mobile.html` 有独立的加载逻辑（轮询等待Babel编译完成+全局错误捕获）

## 六、组件架构详解

### 6.1 主应用组件（app.jsx）

`app.jsx` 是整个应用的核心，负责：

1. **响应式检测**：`isMobile` 状态 + resize 监听
2. **全局状态**：10大板块的导航状态、编辑器状态、日历状态等
3. **布局渲染**：侧边栏 + 顶部栏 + 主内容区
4. **路由切换**：根据 `activeNav` 渲染对应板块
5. **知识库容错**：`window.KNOWLEDGE_BASE || {notes:{},folders:[]}` 容错处理
6. **全局联动**：新建笔记、升维等动作触发全局状态更新

### 6.2 板块组件标准结构

每个功能板块遵循统一的组件结构：

```
*-view.jsx（视图层）
├── 函数签名：function XxxView({ density, isNight, textColor, ... })
├── 响应式状态：const [isMobile, setIsMobile] = useState(innerWidth <= 768)
├── 局部状态：activeTab, selectedItem, filter, ...
├── 数据获取：从 *-data.jsx 导入的全局变量
├── 全局状态订阅：useAppState(selector)
├── 事件处理：handleSelect, handleFilter, ...
└── return：JSX 渲染（根容器 flex:1 + 响应式布局）

*-data.jsx（数据层）
├── 模拟数据定义：const XXX_DATA = { ... }
├── 数据结构设计：符合板块的业务逻辑
└── 全局暴露：Object.assign(window, { XXX_DATA })
```

## 八、已知技术债务与未来优化方向

### 8.1 当前技术债务

| 债务 | 影响 | 优先级 |
|------|------|--------|
| Babel Standalone 体积大（2.99MB） | 首屏加载慢，移动端首次编译需3-5秒 | 高 |
| 无构建优化 | 生产环境性能不佳 | 中 |
| 数据全为模拟数据 | 无真实数据持久化 | 高 |
| 无后端服务 | 无法多端同步 | 中 |
| 语音ASR/TTS为模拟实现 | 无真实语音能力 | 中 |
| AI对话为模拟实现 | 无真实AI能力 | 高 |
| 知识图谱无拖拽/缩放 | 移动端交互受限 | 中 |
| 部分组件内联样式与CSS冲突 | 维护成本高 | 低 |

### 8.2 未来优化方向

1. **引入 Vite 构建**：生产环境使用 Vite 打包，开发环境保持零构建
2. **本地数据持久化**：IndexedDB / localStorage 存储笔记和设置
3. **后端服务**：Rust 实现的本地优先同步服务（参考技术设计文档）
4. **真实AI集成**：接入本地大模型（Ollama / llama.cpp）
5. **真实语音集成**：接入 Web Speech API / 本地ASR
6. **知识图谱交互优化**：力导向布局、拖拽、缩放、路径探索
7. **PWA 支持**：离线可用、添加到主屏幕、推送通知（零打扰前提下）

## 九、总结

OneOS V1 的技术架构有以下核心特点：

1. **零构建依赖**：降低入门门槛，快速迭代
2. **数据与视图分离**：每个板块都有独立的数据层和视图层
3. **全局状态联动**：发布订阅模式实现板块间数据自动联动
4. **统一设计系统**：设计令牌确保视觉一致性
5. **一套代码双端适配**：isMobile状态 + CSS媒体查询 + 设计系统覆盖
6. **本地优先**：所有依赖本地化，数据存储在本地
7. **10大板块有机整体**：不是功能堆砌，而是围绕核心哲学的有机整体

**OneOS 的技术架构服务于它的哲学：工具服务于人，而非人服务于工具。** 每一个技术选择，都是为了让用户能够更深度地思考、更真实地连接、更清晰地看到自己的成长。
