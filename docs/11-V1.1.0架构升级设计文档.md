## 1. 现状分析

### 1.1 当前架构概览

OneOS V1.0.0采用的是**单页应用 + 全局可变状态**的架构模式：

```
┌─────────────────────────────────────────────────────────┐
│                    index.html / mobile.html               │
├─────────────────────────────────────────────────────────┤
│                    window 全局对象                         │
│  ┌──────────────┐ ┌──────────────┐ ┌─────────────────┐ │
│  │ KNOWLEDGE_   │ │ DataAdapter  │ │ OneOSAppState   │ │
│  │ BASE (数据)  │ │ (IndexedDB)  │ │ (全局状态)      │ │
│  └──────┬───────┘ └──────┬───────┘ └────────┬────────┘ │
│         │                 │                    │          │
├─────────┴─────────────────┴────────────────────┴──────────┤
│                     App.jsx (上帝组件)                      │
│  30+ useState · 10+ useEffect · 所有业务逻辑 · 所有事件处理 │
├─────────────────────────────────────────────────────────────┤
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────┐ │
│  │Dashboard│ │ Editor  │ │ Graph   │ │Calendar │ │ AI  │ │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────┘ │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐         │
│  │ Social  │ │ Voice   │ │ Search  │ │ Settings│         │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘         │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 核心问题诊断

#### 问题1：上帝组件（God Component）

**现象**：`app.jsx` 包含：
- 32个 `useState` 状态变量
- 8个 `useEffect` 副作用
- 15+ 业务处理函数（handleNewNote、handleContentChange等）
- 所有导航切换、键盘快捷键、Toast通知逻辑
- 直接操作 `window.KNOWLEDGE_BASE`、`window.DataAdapter`、`window.OneOSAppState`

**代码行数**：~800行（仅JSX部分，不含样式）

**危害**：
- 任何功能变更都需要修改app.jsx，冲突风险高
- 状态变更路径不清晰，难以追踪bug
- 无法对单个功能进行单元测试
- 组件重渲染范围大，性能隐患

#### 问题2：三个全局数据源并存

| 数据源 | 类型 | 用途 | 问题 |
|--------|------|------|------|
| `window.KNOWLEDGE_BASE` | 全局可变对象 | 笔记/文件夹/标签的内存数据 | 任何组件可直接修改，无变更通知 |
| `window.DataAdapter` | 全局单例 | IndexedDB持久化 | 与KB.notes双写，同步逻辑复杂 |
| `window.OneOSAppState` | 发布订阅对象 | 日历/仪表盘联动状态 | 使用不统一，部分组件不知道它的存在 |

**典型问题场景**（新建笔记）：
```javascript
// app.jsx handleNewNote 中同时操作三个数据源：
KB.notes[newId] = newNote;                    // 1. 直接修改全局对象
dailyFolder.children.unshift({...});           // 2. 直接修改嵌套对象
window.DataAdapter.createNote(newNote);        // 3. 异步写入IndexedDB
window.OneOSAppState.addNote({...});           // 4. 发布订阅通知
setStats(prev => ({...}));                     // 5. React状态更新
```

**危害**：
- 五个操作不在一个事务中，任何一步失败都会导致数据不一致
- 没有变更日志，无法追踪"这个笔记是什么时候、被谁创建的"
- 新开发者需要同时理解三个数据源才能正确写代码

#### 问题3：模块间隐式通信

**现象**：
- 编辑器修改笔记内容 → 直接修改 `KB.notes[id].content` → 知识图谱重新读取 `KB.notes` 构建图谱
- 日历强度变化 → 通过 `window.OneOSAppState.subscribe` 通知 → app.jsx更新 `calMonthData`
- 新建笔记 → 通过 `window.dispatchEvent(new CustomEvent('editor-new-note'))` 通知

**危害**：
- 模块间依赖关系不清晰，修改一个模块可能意外影响另一个
- 没有明确的接口定义，重构困难
- 事件名称、数据格式没有统一规范

#### 问题4：Prop Drilling（属性钻取）

**现象**：app.jsx的状态通过props一层层传递给子组件：
```
App (activeNoteId, currentNote, handleContentChange, ...)
 └─ EditorView (15+ props)
     └─ Editor (10+ props)
         └─ WysiwygEditor (8+ props)
             └─ ...
```

**危害**：
- 中间组件不需要这些props，但必须传递，增加耦合
- 修改一个状态需要修改多层组件
- 难以追踪状态的来源和变更路径

#### 问题5：缺乏统一的错误处理

**现象**：
- 部分操作有try-catch，部分直接抛错
- DataAdapter的异步操作有.catch，但只console.error
- 没有全局错误边界（Error Boundary）
- 用户操作失败时没有友好的错误提示

### 1.3 问题严重程度评估

| 问题 | 严重程度 | 影响范围 | 修复难度 | V1.1.0优先级 |
|------|----------|----------|----------|-------------|
| 上帝组件 | 🔴 高 | 全局 | 高 | P0 |
| 三数据源并存 | 🔴 高 | 数据层 | 高 | P0 |
| 模块隐式通信 | 🟠 中 | 模块间 | 中 | P1 |
| Prop Drilling | 🟠 中 | 组件树 | 低 | P0（状态管理引入后自动解决） |
| 错误处理 | 🟡 低 | 全局 | 低 | P1 |

## 2. 架构升级目标

### 2.1 总体目标

> **将OneOS从"全局可变状态 + 上帝组件"架构，升级为"统一状态管理 + 模块化 + 面向接口"架构，为V1.2.0的AI智能化和V1.3.0的插件化奠定基础。**

### 2.2 具体目标

| 目标 | 衡量标准 | V1.1.0达成度 |
|------|----------|-------------|
| **统一状态管理** | 消除window全局状态对象，所有状态通过Store管理 | 100% |
| **消除上帝组件** | app.jsx行数≤200行，仅负责布局和路由 | 100% |
| **模块解耦** | 模块间通过明确的接口/事件通信，无直接依赖 | 80%（核心模块） |
| **数据层统一** | 单一数据源（Repository模式），消除双写 | 100% |
| **插件化预留** | 核心逻辑与插件接口分离，插件API设计完成 | 设计完成，不实现 |
| **可测试性** | 核心逻辑可单元测试，测试覆盖率≥60% | 核心模块≥80% |
| **可维护性** | 新功能开发不需要修改app.jsx | 100% |

### 2.3 设计原则

#### 原则1：单一数据源（Single Source of Truth）

> 所有应用状态存储在统一的Store中，组件从Store读取状态，通过dispatch action修改状态。

- 消除 `window.KNOWLEDGE_BASE`、`window.OneOSAppState` 等全局可变对象
- `window.DataAdapter` 降级为Repository层的内部实现，不对外暴露
- 组件不直接操作数据，通过Store的action修改

#### 原则2：分层架构（Layered Architecture）

> 严格的分层，上层依赖下层，下层不依赖上层。

```
┌─────────────────────────────────────────┐
│           Presentation Layer             │  React组件、UI逻辑
│  (Components / Views / Pages)           │  只负责渲染和用户交互
├─────────────────────────────────────────┤
│           Application Layer              │  Store、Action、业务编排
│  (Stores / Actions / UseCases)          │  业务逻辑、状态管理
├─────────────────────────────────────────┤
│           Domain Layer                   │  领域模型、领域服务
│  (Models / Services / Repositories)     │  核心业务规则、数据抽象
├─────────────────────────────────────────┤
│           Infrastructure Layer           │  IndexedDB、LocalStorage
│  (IndexedDB / Storage / API)            │  具体技术实现
└─────────────────────────────────────────┘
```

**依赖方向**：Presentation → Application → Domain → Infrastructure
**禁止反向依赖**：Domain层不能import React组件，Infrastructure层不能import Store

#### 原则3：面向接口编程（Interface-Oriented）

> 模块间通过接口通信，不依赖具体实现。

- Repository接口定义在Domain层，实现在Infrastructure层
- 模块间通过事件总线（Event Bus）通信，不直接引用
- 插件API通过接口定义，核心不依赖具体插件

#### 原则4：渐进式迁移（Incremental Migration）

> 不搞大爆炸式重写，分模块逐步迁移，每个阶段都保持可运行。

- 先搭建新架构骨架，旧代码继续运行
- 逐个模块迁移到新架构
- 迁移过程中通过适配层兼容新旧代码
- 每个模块迁移完成后立即测试验证

## 3. 状态管理方案

### 3.1 技术选型：Zustand

| 候选方案 | 优势 | 劣势 | 结论 |
|----------|------|------|------|
| **Zustand** | API极简、无样板代码、TS友好、包小(1KB)、支持中间件 | 生态不如Redux成熟 | ✅ 选中 |
| Redux Toolkit | 生态成熟、DevTools强大 | 样板代码多、概念多、包大 | ❌ 过重 |
| Jotai | 原子化、细粒度更新 | 概念新、学习曲线、调试困难 | ❌ 不适合大型应用 |
| Recoil | Facebook出品、原子化 | 维护不活跃、包较大 | ❌ 风险高 |
| React Context | 内置、无依赖 | 性能差（全局重渲染）、无DevTools | ❌ 已被证明不适合 |

**选择Zustand的核心理由**：
1. **极简API**：`create((set, get) => ({...}))`，10分钟上手
2. **无Provider**：不需要包裹组件树，可在非React环境使用
3. **细粒度订阅**：组件只订阅需要的状态，避免不必要重渲染
4. **中间件生态**：persist（持久化）、devtools（调试）、immer（不可变更新）
5. **TypeScript友好**：类型推断优秀，不需要额外类型声明
6. **包体积小**：压缩后仅1KB，不影响首屏加载

### 3.2 Store设计

#### 3.2.1 Store划分原则

- **按领域划分**：每个业务领域一个Store，不按组件划分
- **高内聚低耦合**：相关的状态和action放在一起，Store间依赖最小化
- **单一职责**：每个Store只负责一个领域的状态管理

#### 3.2.2 Store清单

| Store | 职责 | 核心状态 | 核心Action |
|-------|------|----------|------------|
| **useAppStore** | 应用全局状态 | 导航、响应式、主题、Toast、加载状态 | setActiveNav、showToast、setIsMobile |
| **useNoteStore** | 笔记领域 | 笔记列表、当前笔记、编辑器状态、文件夹、标签 | createNote、updateNote、deleteNote、setActiveNote |
| **useEditorStore** | 编辑器状态 | 编辑模式、右面板tab、保存状态、专注模式 | setEditMode、setRightTab、setIsSaving |
| **useCalendarStore** | 日历领域 | 视图模式、年月、选中日期、月数据、颜色方案 | setViewMode、changeMonth、selectDate |
| **useGraphStore** | 知识图谱 | 节点、边、布局状态、选中节点、缩放平移 | setNodes、setEdges、setSelectedNode |
| **useSearchStore** | 全局搜索 | 搜索状态、搜索词、搜索结果、筛选条件 | openSearch、closeSearch、setQuery |
| **useSettingsStore** | 设置 | 所有用户设置、设置面板状态 | updateSettings、openSettings、closeSettings |
| **useAIStore** | AI对话 | 对话列表、当前对话、消息、流式状态、人设 | createConversation、sendMessage、setPersona |
| **useSocialStore** | 社交 | 联系人、消息、圈子、动态 | addContact、sendMessage、joinCircle |
| **useVoiceStore** | 语音交互 | 录音状态、识别结果、TTS状态、权限 | startRecording、stopRecording、speak |

#### 3.2.3 Store依赖关系

```
useAppStore (全局，无依赖)
    │
    ├── useNoteStore (依赖useAppStore的导航)
    │       ├── useEditorStore (依赖useNoteStore的当前笔记)
    │       └── useGraphStore (依赖useNoteStore的笔记数据)
    │
    ├── useCalendarStore (独立)
    ├── useSearchStore (依赖useNoteStore/useCalendarStore等搜索源)
    ├── useSettingsStore (独立)
    ├── useAIStore (依赖useNoteStore的RAG检索)
    ├── useSocialStore (独立)
    └── useVoiceStore (独立)
```

**规则**：
- Store间通过 `useStore.getState()` 读取其他Store状态，不通过props
- Store间通过action调用修改状态，不直接修改其他Store的state
- 避免循环依赖（A→B→A）

### 3.3 核心Store示例

#### 3.3.1 useNoteStore（笔记领域Store）

```typescript
// src/stores/note-store.ts
import { create } from 'zustand';
import { immer } from 'zustand/middleware-immer';
import { noteRepository } from '@/domain/repositories/note-repository';
import type { Note, Folder, Tag } from '@/domain/models/note';

interface NoteState {
  // 状态
  notes: Map<string, Note>;           // 所有笔记（Map，O(1)查找）
  folders: Folder[];                   // 文件夹树
  tags: Tag[];                         // 标签列表
  activeNoteId: string | null;         // 当前编辑的笔记ID
  isLoading: boolean;                  // 加载状态
  error: string | null;                // 错误信息
  
  // 计算属性（通过selector获取）
  // get activeNote(): Note | null
  // get noteList(): Note[]
  
  // Action
  loadNotes: () => Promise<void>;
  createNote: (input: CreateNoteInput) => Promise<Note>;
  updateNote: (id: string, patch: Partial<Note>) => Promise<void>;
  deleteNote: (id: string) => Promise<void>;
  setActiveNote: (id: string | null) => void;
  createFolder: (name: string, parentId?: string) => Promise<Folder>;
  addTag: (name: string) => void;
}

export const useNoteStore = create<NoteState>()(
  immer((set, get) => ({
    notes: new Map(),
    folders: [],
    tags: [],
    activeNoteId: null,
    isLoading: false,
    error: null,
    
    loadNotes: async () => {
      set({ isLoading: true, error: null });
      try {
        const { notes, folders, tags } = await noteRepository.loadAll();
        set({ 
          notes: new Map(notes.map(n => [n.id, n])),
          folders,
          tags,
          isLoading: false 
        });
      } catch (err) {
        set({ isLoading: false, error: (err as Error).message });
      }
    },
    
    createNote: async (input) => {
      const note = await noteRepository.create(input);
      set(state => {
        state.notes.set(note.id, note);
        state.activeNoteId = note.id;
      });
      // 发布领域事件（模块间通信）
      eventBus.emit('note:created', note);
      return note;
    },
    
    updateNote: async (id, patch) => {
      const updated = await noteRepository.update(id, patch);
      set(state => {
        state.notes.set(id, updated);
      });
      eventBus.emit('note:updated', updated);
    },
    
    // ... 其他action
  }))
);

// Selector（计算属性）
export const selectActiveNote = (state: NoteState) => 
  state.activeNoteId ? state.notes.get(state.activeNoteId) ?? null : null;

export const selectNoteList = (state: NoteState) => 
  Array.from(state.notes.values()).sort((a, b) => 
    new Date(b.updatedAt).getTime() - new Date(a.updatedAt).getTime()
  );
```

#### 3.3.2 useAppStore（应用全局Store）

```typescript
// src/stores/app-store.ts
import { create } from 'zustand';
import { persist } from 'zustand/middleware';

interface AppState {
  // 导航
  activeNav: string;
  setActiveNav: (nav: string) => void;
  
  // 响应式
  isMobile: boolean;
  setIsMobile: (isMobile: boolean) => void;
  
  // 主题
  theme: 'light' | 'dark';
  setTheme: (theme: 'light' | 'dark') => void;
  
  // Toast
  toast: { message: string; type: 'info' | 'success' | 'error' } | null;
  showToast: (message: string, type?: 'info' | 'success' | 'error') => void;
  hideToast: () => void;
  
  // 全局加载
  isGlobalLoading: boolean;
  setGlobalLoading: (loading: boolean) => void;
}

export const useAppStore = create<AppState>()(
  persist(
    (set) => ({
      activeNav: 'dashboard',
      isMobile: typeof window !== 'undefined' ? window.innerWidth <= 768 : false,
      theme: 'light',
      toast: null,
      isGlobalLoading: false,
      
      setActiveNav: (activeNav) => set({ activeNav }),
      setIsMobile: (isMobile) => set({ isMobile }),
      setTheme: (theme) => set({ theme }),
      
      showToast: (message, type = 'info') => {
        set({ toast: { message, type } });
        setTimeout(() => set({ toast: null }), 2500);
      },
      hideToast: () => set({ toast: null }),
      
      setGlobalLoading: (isGlobalLoading) => set({ isGlobalLoading }),
    }),
    {
      name: 'oneos-app-storage',
      partialize: (state) => ({ theme: state.theme }), // 只持久化theme
    }
  )
);
```

### 3.4 组件使用模式

#### 3.4.1 正确模式：细粒度订阅

```tsx
// ✅ 好：只订阅需要的状态，避免不必要重渲染
function EditorToolbar() {
  const editMode = useEditorStore(state => state.editMode);
  const setEditMode = useEditorStore(state => state.setEditMode);
  const isSaving = useEditorStore(state => state.isSaving);
  
  return (
    <div>
      <span>{isSaving ? '保存中...' : '已保存'}</span>
      <button onClick={() => setEditMode('wysiwyg')}>所见即所得</button>
      <button onClick={() => setEditMode('markdown')}>Markdown</button>
    </div>
  );
}
```

#### 3.4.2 错误模式：全量订阅

```tsx
// ❌ 坏：整个state变化都会导致重渲染
function EditorToolbar() {
  const { editMode, setEditMode, isSaving, rightTab, ... } = useEditorStore();
  // ...
}
```

## 4. 模块解耦方案

### 4.1 模块划分

#### 4.1.1 核心模块清单

| 模块 | 职责 | 对外接口 | 依赖 |
|------|------|----------|------|
| **笔记模块** | 笔记的CRUD、文件夹、标签、反向链接 | NoteService、NoteRepository | 无（核心） |
| **编辑器模块** | 笔记编辑、WYSIWYG、Markdown解析 | EditorComponent、EditorService | 笔记模块 |
| **知识图谱模块** | 图谱构建、布局、可视化 | GraphService、GraphComponent | 笔记模块 |
| **日历模块** | 日历视图、日程、强度统计 | CalendarService、CalendarComponent | 笔记模块 |
| **搜索模块** | 全文搜索、模糊匹配、搜索历史 | SearchService | 笔记/日历/AI模块 |
| **AI模块** | AI对话、RAG检索、人设系统 | AIService、AIComponent | 笔记模块（RAG） |

### 4.2 模块间通信：事件总线（Event Bus）

#### 4.2.1 为什么用事件总线

模块间不直接引用，通过事件总线发布/订阅事件：
- **解耦**：发布者不知道订阅者是谁，订阅者不知道发布者是谁
- **可扩展**：新增订阅者不需要修改发布者
- **可测试**：可以单独测试事件发布和订阅
- **可追踪**：所有事件经过总线，可以记录和调试

#### 4.2.2 事件总线设计

```typescript
// src/shared/kernel/event-bus.ts
type EventHandler<T = any> = (payload: T) => void;

class EventBus {
  private handlers = new Map<string, Set<EventHandler>>();
  
  // 发布事件
  emit<T>(event: string, payload: T): void {
    const handlers = this.handlers.get(event);
    if (handlers) {
      handlers.forEach(handler => {
        try {
          handler(payload);
        } catch (err) {
          console.error(`[EventBus] 事件 ${event} 处理失败:`, err);
        }
      });
    }
  }
  
  // 订阅事件
  on<T>(event: string, handler: EventHandler<T>): () => void {
    if (!this.handlers.has(event)) {
      this.handlers.set(event, new Set());
    }
    this.handlers.get(event)!.add(handler);
    return () => this.off(event, handler); // 返回取消订阅函数
  }
  
  // 取消订阅
  off<T>(event: string, handler: EventHandler<T>): void {
    this.handlers.get(event)?.delete(handler);
  }
  
  // 一次性订阅
  once<T>(event: string, handler: EventHandler<T>): () => void {
    const wrapper = (payload: T) => {
      handler(payload);
      this.off(event, wrapper);
    };
    return this.on(event, wrapper);
  }
}

export const eventBus = new EventBus();
```

#### 4.2.3 事件命名规范

**格式**：`领域:动作`（小写，冒号分隔）

| 事件 | 发布者 | 订阅者 | Payload |
|------|--------|--------|---------|
| `note:created` | 笔记模块 | 知识图谱、搜索、日历、仪表盘 | Note |
| `note:updated` | 笔记模块 | 知识图谱、搜索 | Note |
| `note:deleted` | 笔记模块 | 知识图谱、搜索、编辑器 | { id } |
| `note:selected` | 编辑器/搜索 | 编辑器、知识图谱 | { id } |
| `calendar:date-selected` | 日历模块 | 日详情面板 | { date } |
| `search:navigate` | 搜索模块 | 应用导航 | { navId } |
| `ai:message-sent` | AI模块 | 日历（强度）、笔记（保存） | Message |
| `settings:changed` | 设置模块 | 全局（主题/密度/字号） | Settings |

#### 4.2.4 React中使用事件总线


```typescript
// src/infrastructure/repositories/indexeddb-note-repository.ts
export class IndexedDBNoteRepository implements NoteRepository {
  private db: IDBDatabase | null = null;
  private cache = new Map<string, Note>(); // 内存缓存
  
  async findById(id: string): Promise<Note | null> {
    // 先查缓存
    if (this.cache.has(id)) return this.cache.get(id)!;
    // 缓存未命中，查IndexedDB
    const note = await this.dbGet('notes', id);
    if (note) this.cache.set(id, note); // 写入缓存
    return note;
  }
  
  async create(note: Note): Promise<Note> {
    await this.dbPut('notes', note);
    this.cache.set(note.id, note); // 更新缓存
    return note;
  }
  
  // ... 其他方法
}
```

```typescript
interface Migration {
  version: number;           // 目标版本
  name: string;
  up(db: IDBDatabase): Promise<void>;  // 升级
  down?(db: IDBDatabase): Promise<void>; // 降级（可选）
}

class MigrationManager {
  private migrations: Migration[] = [
    { version: 1, name: 'initial', up: async () => {} },
    { version: 2, name: 'add-sync-fields', up: addSyncFieldsMigration },
    { version: 3, name: 'add-note-type', up: addNoteTypeMigration },
  ];
  
  async migrate(): Promise<void> {
    const currentVersion = await this.getCurrentVersion();
    const pending = this.migrations.filter(m => m.version > currentVersion);
    
    for (const migration of pending) {
      console.log(`[Migration] 执行: v${migration.version} - ${migration.name}`);
      await migration.up(this.db);
      await this.setCurrentVersion(migration.version);
    }
  }
}
```

### 8.3 迁移期间的兼容策略

#### 策略1：新旧并存，逐步切换

- 新架构和旧代码同时存在，通过适配层兼容
- 每个模块迁移完成后，切换到新实现，旧代码保留一个版本
- 全部迁移完成后，统一删除旧代码

#### 策略2：适配器模式

```typescript
// 适配层：新Store → 旧全局对象
// 在迁移期间，新Store的变更同步到旧全局对象，保证未迁移的组件正常工作
useNoteStore.subscribe((state) => {
  // 同步到window.KNOWLEDGE_BASE（兼容未迁移的组件）
  window.KNOWLEDGE_BASE.notes = Object.fromEntries(state.notes);
});
```

#### 策略3：特性开关

```typescript
// 通过特性开关控制使用新架构还是旧架构
const USE_NEW_ARCH = true; // 开发期间可切换

if (USE_NEW_ARCH) {
  // 新架构实现
} else {
  // 旧架构实现（兼容）
}
```

## 10. 附录

### 10.1 术语表

| 术语 | 定义 |
|------|------|
| **Store** | Zustand的状态容器，包含状态和action |
| **Action** | 修改状态的方法，通过dispatch调用 |
| **Selector** | 从Store中选取部分状态的函数 |
| **Repository** | 数据访问层，封装具体存储实现 |
| **Service** | 领域服务，包含业务逻辑 |
| **Event Bus** | 事件总线，模块间发布/订阅事件的机制 |
| **DI Container** | 依赖注入容器，管理服务的创建和获取 |
| **God Component** | 上帝组件，承担过多职责的大型组件 |
| **Prop Drilling** | 属性钻取，状态通过多层组件props传递的现象 |
| **Single Source of Truth** | 单一数据源，所有状态来自统一的Store |
| **Extension Point** | 扩展点，插件可以挂载的位置 |
