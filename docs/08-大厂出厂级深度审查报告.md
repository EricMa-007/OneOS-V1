#### 🔴 #1 切换笔记时编辑器内容不更新（高严重度）

**文件**: components/wysiwyg-editor.jsx 第55-69行

**问题描述**:
初始化编辑器内容的useEffect依赖数组为空`[]`，但使用了`initialContent`和`mode`。当用户切换笔记时，initialContent变化，但useEffect不会重新执行，导致编辑器显示旧笔记的内容。

**用户影响**:
- 切换笔记后，编辑器仍然显示上一篇笔记的内容
- 用户可能误以为切换失败，或者在错误的笔记上编辑
- 可能导致数据混乱，编辑的内容保存到错误的笔记

**修复方案**:
将useEffect依赖数组从`[]`改为`[initialContent, mode]`，并在effect中同步content状态：
```javascript
React.useEffect(() => {
  if (editorRef.current && mode === 'wysiwyg') {
    // ... 渲染逻辑
  }
  setContent(initialContent); // 同步content状态
}, [initialContent, mode]);
```

**验证**: 切换笔记时编辑器内容正确更新，content状态同步。

#### 🟠 #2 页面卸载时异步保存可能无法完成（中严重度）

**文件**: src/data-adapter.js 第415-423行

**问题描述**:
`saveBeforeUnload`函数在`beforeunload`事件中调用异步的`flushPendingNotes()`，但IndexedDB操作是异步的，页面卸载时可能无法完成，导致待保存的数据丢失。

**用户影响**:
- 用户快速关闭页面或刷新时，最近编辑的内容可能丢失
- 自动保存的1.5秒防抖窗口内的内容可能丢失
- 数据丢失不可恢复

**修复方案**:
1. 使用`visibilitychange`事件替代`beforeunload`，在页面隐藏时就开始保存，有更多时间完成异步操作
2. 添加`emergencySave`函数，在`beforeunload`时将待保存数据同步保存到`localStorage`作为兜底
3. 添加`restoreEmergencySave`函数，在应用初始化时从`localStorage`恢复数据
4. 三重保护：visibilitychange异步保存 → beforeunload同步兜底 → 启动时恢复

**验证**: 快速关闭页面后重新打开，数据完整恢复。

#### 🟠 #3 handleSave闭包可能捕获旧的content状态（中严重度）

**文件**: components/wysiwyg-editor.jsx 第96-115行

**问题描述**:
`handleSave`使用`useCallback`依赖`[content, onSave]`，每次content变化时重新创建。但`handleContentChange`的依赖是`[onChange, largeFileMode]`，不包含`handleSave`，因此在防抖定时器中调用的`handleSave`可能是旧版本，捕获的是旧的content状态。

**用户影响**:
- 快速连续输入时，保存的可能是旧版本的内容
- 最新的输入可能丢失
- 保存的内容与编辑器显示的内容不一致

**修复方案**:
使用`contentRef`保存最新的content，`handleSave`从ref读取而不是从闭包捕获：
```javascript
const contentRef = React.useRef(initialContent);
React.useEffect(() => { contentRef.current = content; }, [content]);

const handleSave = React.useCallback(async () => {
  await onSave(contentRef.current); // 从ref读取最新content
}, [onSave]);
```

**验证**: 快速连续输入后保存，内容完整无丢失。

#### 🟠 #4 性能监控useEffect依赖为空（中严重度）

**文件**: components/wysiwyg-editor.jsx 第28-52行

**问题描述**:
性能监控的useEffect依赖数组为空`[]`，但使用了`initialContent`进行大文件检测。切换笔记时，如果新笔记是大文件，不会重新启用大文件模式。

**用户影响**:
- 切换到大文件笔记时，大文件模式未启用
- 保存延迟仍然是1.5秒而不是3秒
- 可能导致大文件编辑时性能下降

**修复方案**:
将useEffect依赖数组从`[]`改为`[initialContent]`，并在大文件检测不通过时关闭大文件模式：
```javascript
React.useEffect(() => {
  // ... 性能监控逻辑
  const fileInfo = window.PerformanceOptimizer.detectFileSize(initialContent);
  if (fileInfo.shouldOptimize) {
    setLargeFileMode(true);
  } else {
    setLargeFileMode(false); // 切换到小文件时关闭大文件模式
  }
}, [initialContent]);
```

**验证**: 切换到大文件笔记时自动启用大文件模式，切换到小文件时关闭。

#### 🟠 #5 htmlToMarkdown正则无法正确处理多行内容（中严重度）

**文件**: components/wysiwyg-editor.jsx 第171-214行

**问题描述**:
htmlToMarkdown函数中大多数正则使用`(.*?)`非贪婪匹配，但默认情况下`.`不匹配换行符。对于块级元素如`<p>`、`<blockquote>`、`<li>`，如果内容跨越多行，可能无法正确匹配，导致内容丢失。

**用户影响**:
- 包含多行内容的段落、引用、列表项转换为Markdown时可能丢失部分内容
- 保存的Markdown内容不完整
- 重新打开笔记时内容缺失

**修复方案**:
将所有`(.*?)`改为`([\s\S]*?)`，支持匹配换行符：
```javascript
md = md.replace(/<p[^>]*>([\s\S]*?)<\/p>/gi, '$1\n\n');
```

同时优化代码块处理，优先处理避免内部标签被转换。

**验证**: 包含多行内容的段落、引用、列表项正确转换为Markdown。

#### 🟠 #6 htmlToMarkdown图片正则无法匹配alt在src之前的情况（中严重度）

**文件**: components/wysiwyg-editor.jsx 第197行

**问题描述**:
图片正则`<img[^>]*src="([^"]*)"[^>]*alt="([^"]*)"[^>]*>`假设src在alt之前，但浏览器生成的HTML可能alt在src之前，或者没有alt属性，导致图片无法正确转换。

**用户影响**:
- alt在src之前的图片转换为Markdown时丢失
- 没有alt属性的图片转换为Markdown时丢失
- 保存的Markdown内容缺少图片

**修复方案**:
使用函数式替换，分别提取src和alt，不依赖顺序：
```javascript
md = md.replace(/<img[^>]*>/gi, (match) => {
  const srcMatch = match.match(/src=["']([^"']*)["']/i);
  const altMatch = match.match(/alt=["']([^"']*)["']/i);
  const src = srcMatch ? srcMatch[1] : '';
  const alt = altMatch ? altMatch[1] : '';
  return src ? `![${alt}](${src})` : '';
});
```

**验证**: alt在src之前、没有alt属性的图片都能正确转换。

#### 🟡 #7 flushPendingNotes没有重试机制（低严重度）

**文件**: src/data-adapter.js 第252-267行

**问题描述**:
`flushPendingNotes`保存失败时只记录错误，没有重试机制。如果IndexedDB暂时不可用（如磁盘满、浏览器限制），待保存的数据会一直积压在内存中，页面关闭后丢失。

**修复方案**:
添加重试机制，最多重试3次，每次间隔500ms。重试3次后仍失败，将数据保存到localStorage作为兜底：
```javascript
async function flushPendingNotes(retryCount = 0) {
  try {
    // ... 保存逻辑
  } catch (err) {
    if (retryCount < 3) {
      await new Promise(resolve => setTimeout(resolve, 500));
      await flushPendingNotes(retryCount + 1);
    } else {
      // 保存到localStorage兜底
      localStorage.setItem('oneos_pending_notes', JSON.stringify(pendingNotes));
    }
  }
}
```

**验证**: 模拟IndexedDB保存失败，重试3次后数据保存到localStorage。

#### 🟡 #8 initDataLayer没有完整的try-catch（低严重度）

**文件**: src/data-adapter.js 第91-121行

**问题描述**:
`initDataLayer`函数没有完整的try-catch包裹，如果`openDatabase`、`count`、`bulkPut`等操作抛出异常，整个初始化会失败，可能导致应用崩溃或白屏。

**修复方案**:
用try-catch包裹整个初始化过程，失败时确保`KNOWLEDGE_BASE`存在，避免应用崩溃：
```javascript
async function initDataLayer() {
  try {
    // ... 初始化逻辑
  } catch (err) {
    console.error('[DataAdapter] 数据层初始化失败:', err);
    if (!window.KNOWLEDGE_BASE) {
      window.KNOWLEDGE_BASE = { notes: {}, folders: [] };
    }
    return window.KNOWLEDGE_BASE;
  }
}
```

**验证**: 模拟IndexedDB初始化失败，应用正常启动，显示空状态。

#### 🟡 #9 createNote ID生成可能重复（低严重度，可接受风险）

**文件**: src/data-adapter.js 第298-332行

**问题描述**:
`createNote`使用`Date.now() + Math.random().toString(36).slice(2, 8)`生成ID，理论上可能重复，但概率极低（约1/21亿）。在正常使用场景下不会发生。

**风险评估**:
- 重复概率：约1/21亿
- 影响：如果重复，新笔记会覆盖旧笔记
- 缓解：Date.now()提供毫秒级时间戳，Math.random()提供6位随机字符，组合后唯一性足够

**处理**: 可接受风险，不修复。如果未来需要更高的唯一性保证，可以使用UUID或crypto.randomUUID()。
