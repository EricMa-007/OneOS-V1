## 六、发现并修复的Bug（共5个）

### Bug #1: SQL优先级错误 — 好友请求重复检测失效

**严重程度**: P1（严重）  
**发现时间**: API层测试阶段  
**影响模块**: 用户与好友模块 — 发送好友请求

**问题描述**:
发送好友请求时，检测是否已有待处理请求的SQL语句存在优先级错误：
```sql
-- 错误的SQL（AND优先级高于OR）
SELECT id FROM friend_requests 
WHERE (from_user_id = ? AND to_user_id = ?) 
   OR (from_user_id = ? AND to_user_id = ?) AND status = ?
```
由于`AND`优先级高于`OR`，实际执行的是：
```sql
WHERE (from_user_id = ? AND to_user_id = ?) 
   OR (from_user_id = ? AND to_user_id = ? AND status = ?)
```
第一个条件没有检查`status`，导致已接受/已拒绝的旧请求也会被匹配到。

**修复方案**:
给OR条件加上括号，确保优先级正确：
```sql
SELECT id FROM friend_requests 
WHERE ((from_user_id = ? AND to_user_id = ?) 
    OR (from_user_id = ? AND to_user_id = ?)) AND status = ?
```

**修复文件**: `server/src/routes/users.js` 第103行

### Bug #2: 删除好友时未清理好友请求记录 — 唯一约束冲突导致500错误

**严重程度**: P0（致命）  
**发现时间**: 双用户交互模拟测试阶段  
**影响模块**: 用户与好友模块 — 删除好友、重新发送好友请求

**问题描述**:
`friend_requests`表有唯一约束`UNIQUE(from_user_id, to_user_id)`。删除好友时只删除了`friendships`表中的记录，但`friend_requests`表中的记录（状态为'accepted'）仍然存在。

当用户删除好友后重新发送好友请求时，由于唯一约束冲突，INSERT操作失败，导致服务器返回500错误，且错误信息为空（全局错误处理未正确返回）。

**复现步骤**:
1. 用户A给用户B发送好友请求
2. 用户B接受好友请求
3. 用户A删除用户B好友
4. 用户A重新给用户B发送好友请求 → **500错误**

**修复方案**:
1. 删除好友时，同时清理对应的`friend_requests`记录
2. 发送好友请求时，如果已有记录（不管状态），就更新为新的pending请求，而不是插入新记录
3. 修复全局错误处理，让500错误返回具体错误信息

**修复文件**: 
- `server/src/routes/users.js` — 删除好友接口（第205-218行）
- `server/src/routes/users.js` — 发送好友请求接口（第101-127行）
- `server/src/index.js` — 全局错误处理中间件

### Bug #3: 注册接口未保存bio和topicTags — 用户资料丢失

**严重程度**: P1（严重）  
**发现时间**: 双用户交互模拟测试阶段  
**影响模块**: 认证模块 — 注册、人类节点发现

**问题描述**:
注册接口只接收了`username, password, displayName`三个参数，忽略了`bio`和`topicTags`。数据库插入时`bio`写死为`''`，`topic_tags`写死为`'[]'`。

这导致：
1. 用户注册时设置的个人简介和话题标签全部丢失
2. 人类节点发现功能无法正常工作（所有用户的话题标签都是空的）
3. 数据一致性测试失败

**修复方案**:
1. 注册接口解构`bio`和`topicTags`参数
2. 数据库插入时使用用户传入的值
3. 返回的用户信息中包含正确的`bio`和`topicTags`

**修复文件**: `server/src/routes/auth.js` 第15-62行

### Bug #4: 人类节点发现SQL参数不匹配 — 查询异常

**严重程度**: P1（严重）  
**发现时间**: 双用户交互模拟测试阶段  
**影响模块**: 用户与好友模块 — 人类节点发现

**问题描述**:
人类节点发现的SQL语句有2个`?`占位符（`id != ?`和`user_id = ?`），但`.all()`方法传了3个参数（`req.userId, parseInt(limit) * 3`）。

SQL中的`LIMIT 50`是写死的，不需要参数，但代码错误地传入了第三个参数。这会导致better-sqlite3参数不匹配，可能引发异常或行为异常。

**修复方案**:
1. 移除多余的参数，只传2个参数
2. 将LIMIT改为100，确保有足够的候选用户进行话题交集计算和排序

**修复文件**: `server/src/routes/users.js` 第242-248行

### Bug #5: 注册接口缺少字段长度限制 — 超长输入未处理

**严重程度**: P2（一般）  
**发现时间**: 边界条件测试阶段  
**影响模块**: 认证模块 — 注册

**问题描述**:
注册接口只检查了用户名最小长度（3字符）和密码最小长度（6字符），但没有检查最大长度。超长的用户名（1000字符）、密码、昵称、个人简介可以正常注册，可能导致：
1. 数据库存储异常
2. 前端显示异常
3. 潜在的性能问题

**修复方案**:
添加各字段的最大长度限制：
- 用户名：最多50字符
- 密码：最多100字符
- 昵称：最多100字符
- 个人简介：最多500字符

**修复文件**: `server/src/routes/auth.js` 第22-44行
